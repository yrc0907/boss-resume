# 问题、方案与性能记录

## 记录规则

每个异常绑定唯一 `scenario_id`。记录问题、根因、方案、性能变化和验证结果；如果平台页面改版，优先补充对应适配器，不修改通用评分契约。

## 已处理

### scenario_id: BROWSER_SCROLL_BOUNDARY

- 问题：扩展宿主项目曾出现侧边栏、顶部栏和数据区一起滚动。
- 根因：页面只有文档级滚动容器，内容区没有独立高度和 `overflow-y` 边界。
- 方案：宿主项目将桌面端改为固定外壳，只有数据区滚动；本扩展不依赖宿主页面滚动状态。
- 性能变化：避免重复布局和整页重绘，长列表滚动只影响内容区。
- 验证：桌面和移动端 Playwright 滚动检查通过。

### scenario_id: QUEUE_STATE_RESCAN

- 问题：重新扫描时，已处理的 DOM 节点不会再次装饰。
- 根因：初版使用不可清空的 `WeakSet` 保存已标记节点。
- 方案：改为可清空的 `Set`，重新扫描前清理标记、徽标和按钮。
- 性能变化：正常定时扫描仍跳过已处理节点；只有用户主动刷新时才重新遍历。
- 验证：本地构建和扩展静态检查通过。

### scenario_id: SETTINGS_LIVE_REFRESH

- 问题：弹窗修改筛选条件后，当前岗位页面不会立即更新。
- 根因：设置只写入本地存储，内容脚本没有收到变化通知。
- 方案：后台保存成功后广播 `SETTINGS_UPDATED`，内容脚本重置装饰并重新评分。
- 性能变化：仅在保存动作发生时广播，不增加轮询频率。
- 验证：类型检查通过；真实平台需在人工验收阶段确认。

### scenario_id: MATCH_COUNT_PERSISTENCE

- 问题：定时扫描跳过已处理卡片后，浮层匹配数量会被错误重置为 0。
- 根因：计数只统计当前扫描中新建的装饰，没有统计页面上已经存在的匹配标记。
- 方案：每轮扫描先读取现有 `.bjh-job-match` 数量，再为新匹配卡片递增。
- 性能变化：增加一次轻量 class 查询，避免重复解析岗位文本。
- 验证：构建和静态检查通过；真实平台需在人工验收阶段观察连续两轮扫描。

## 已知风险

### scenario_id: PLATFORM_DOM_DRIFT

- 问题：招聘网站改版可能导致岗位卡片或字段选择器失效。
- 根因：页面 DOM 不是公开稳定 API，且存在登录态、AB 实验和异步列表。
- 方案：每个平台独立适配；选择器按“稳定属性优先、文本兜底”；读取失败显示待确认，不生成虚假字段。
- 性能变化：多个选择器会增加少量 DOM 查询，但只在内容脚本定时扫描时执行。
- 临时方案：用户点击“重新扫描”，等待列表加载后再验收。

### scenario_id: PLATFORM_RATE_LIMIT

- 问题：连续浏览或批量操作可能触发平台限速、验证码或账号风控。
- 根因：平台按频率、设备、IP、账号历史行为综合判断异常。
- 方案：本项目不做无人值守发送、不绕过验证码、不伪造指纹；队列仅用于准备和人工确认。
- 性能变化：牺牲部分自动化速度，换取较低的异常行为密度。
- 临时方案：缩小筛选范围，分批人工确认，遵守各平台服务条款。

### scenario_id: THIRD_PARTY_DATA_LEAK

- 问题：第三方 AI 或未知扩展可能收集简历、Cookie 或账号信息。
- 根因：浏览器扩展拥有页面读取权限，外部服务的隐私边界不可默认信任。
- 方案：默认不调用外部 API；设置、岗位摘要和队列只保存在本地；后续接入 AI 必须显式授权并说明发送字段。
- 性能变化：离线评分延迟低且稳定，但个性化文案能力有限。
- 临时方案：使用本地模板变量生成招呼语，不上传完整简历。

### scenario_id: PLATFORM_ADAPTER_REGISTRY

- 问题：多个招聘网站的岗位卡片结构不同，直接在一个内容脚本里堆选择器会互相污染。
- 根因：平台差异和通用业务规则没有隔离，改一个站点容易影响其他站点。
- 方案：将每个平台拆成 `src/content/adapters/` 下的独立文件，由注册入口按域名选择 `cardSelectors` 和字段选择器；通用层继续只处理评分和队列。
- 性能变化：每个页面只遍历当前平台的选择器，避免无关站点查询。
- 验证：Manifest 已覆盖 11 个目标域名，构建测试校验所有 host permission；真实 DOM 仍需逐站人工验收。

### scenario_id: APPLICATION_FORM_VARIANCE

- 问题：网申表单字段、步骤和自定义控件差异大，单一通用脚本容易误填。
- 根因：表单字段没有统一公开协议，附件、开放问答和验证码还涉及高风险外部操作。
- 方案：作为候选模块采用 DOM 识别优先、站点适配器补充、多模态可选兜底，并展示识别置信度。
- 性能变化：常规字段保持本地即时识别；只有低置信度字段才考虑额外分析。
- 临时方案：当前版本只提供岗位准备和招呼语复制，不自动填写或提交网申。

### scenario_id: LOCAL_DEMO_HOST

- 问题：直接打开 `file://` 演示页时，Chrome 内容脚本不会按真实平台适配器运行。
- 根因：扩展匹配规则默认只覆盖招聘网站 HTTPS 域名，且文件页没有平台 hostname。
- 方案：增加受限的 localhost 演示适配器和 `python -m http.server` 启动方式；不增加任何真实平台权限。
- 性能变化：只对本地演示页面增加一次精确 class 查询。
- 验证：构建测试校验 localhost match；Playwright 加载 `dist` 后访问 `http://localhost:8087/boss-mock.html`，页面出现本地演示浮层和 2 个匹配岗位；真实平台权限不受影响。

### scenario_id: BATCH_QUEUE_ONLY

- 问题：逐个点击岗位卡片加入准备队列仍然影响海投效率。
- 根因：候选岗位筛选结果已经在页面内，但缺少一次性写入本地队列的入口。
- 方案：增加“加入全部匹配”按钮，逐条调用本地队列消息；该流程不打开详情、不点击沟通、不发送消息。
- 性能变化：批量操作只传输已解析的岗位对象，避免重新扫描 DOM；队列仍受 30 条上限保护。
- 验证：静态测试检查批量入口存在；真实平台需由用户在列表页人工验收。

### scenario_id: LOCAL_QUEUE_EXPORT

- 问题：候选岗位只保存在浏览器本地，难以离线复盘和整理。
- 根因：首版只实现队列读写，没有导出边界清晰的结构化记录。
- 方案：弹窗生成 UTF-8 CSV，只导出岗位公开字段、匹配分、状态和岗位链接；使用 Blob 下载，不访问外部接口。
- 性能变化：导出成本与队列条数线性相关，默认上限 30 条，浏览器端即时完成。
- 验证：类型检查和构建测试通过；导出动作仅发生在用户点击“导出 CSV”后。
