# 问题、方案与性能记录

## 记录规则

每个异常绑定唯一 `scenario_id`。记录问题、根因、方案、性能变化和验证结果；如果平台页面改版，优先补充对应适配器，不修改通用评分契约。

## 已处理

### scenario_id: BROWSER_SCROLL_BOUNDARY

- 问题：扩展宿主项目曾出现侧边栏、顶部栏和数据区一起滚动。
- 根因：页面只有文档级滚动容器，内容区没有独立高度和 `overflow-y` 边界。
- 方案：宿主项目将桌面端改为固定外壳，只有数据区滚动；本扩展不依赖宿主页面滚动状态。
- 性能变化：避免重复布局和整页重绘，长列表滚动只影响内容区。
- 验证：桌面和移动端 Playwright 滚动检查通过。

### scenario_id: QUEUE_STATE_RESCAN

- 问题：重新扫描时，已处理的 DOM 节点不会再次装饰。
- 根因：初版使用不可清空的 `WeakSet` 保存已标记节点。
- 方案：改为可清空的 `Set`，重新扫描前清理标记、徽标和按钮。
- 性能变化：正常定时扫描仍跳过已处理节点；只有用户主动刷新时才重新遍历。
- 验证：本地构建和扩展静态检查通过。

### scenario_id: SETTINGS_LIVE_REFRESH

- 问题：弹窗修改筛选条件后，当前岗位页面不会立即更新。
- 根因：设置只写入本地存储，内容脚本没有收到变化通知。
- 方案：后台保存成功后广播 `SETTINGS_UPDATED`，内容脚本重置装饰并重新评分。
- 性能变化：仅在保存动作发生时广播，不增加轮询频率。
- 验证：类型检查通过；真实平台需在人工验收阶段确认。

### scenario_id: MATCH_COUNT_PERSISTENCE

- 问题：定时扫描跳过已处理卡片后，浮层匹配数量会被错误重置为 0。
- 根因：计数只统计当前扫描中新建的装饰，没有统计页面上已经存在的匹配标记。
- 方案：每轮扫描先读取现有 `.bjh-job-match` 数量，再为新匹配卡片递增。
- 性能变化：增加一次轻量 class 查询，避免重复解析岗位文本。
- 验证：构建和静态检查通过；真实平台需在人工验收阶段观察连续两轮扫描。

## 已知风险

### scenario_id: PLATFORM_DOM_DRIFT

- 问题：招聘网站改版可能导致岗位卡片或字段选择器失效。
- 根因：页面 DOM 不是公开稳定 API，且存在登录态、AB 实验和异步列表。
- 方案：每个平台独立适配；选择器按“稳定属性优先、文本兜底”；读取失败显示待确认，不生成虚假字段。
- 性能变化：多个选择器会增加少量 DOM 查询，但只在内容脚本定时扫描时执行。
- 临时方案：用户点击“重新扫描”，等待列表加载后再验收。

### scenario_id: PLATFORM_RATE_LIMIT

- 问题：连续浏览或批量操作可能触发平台限速、验证码或账号风控。
- 根因：平台按频率、设备、IP、账号历史行为综合判断异常。
- 方案：本项目不做无人值守发送、不绕过验证码、不伪造指纹；队列仅用于准备和人工确认。
- 性能变化：牺牲部分自动化速度，换取较低的异常行为密度。
- 临时方案：缩小筛选范围，分批人工确认，遵守各平台服务条款。

### scenario_id: THIRD_PARTY_DATA_LEAK

- 问题：第三方 AI 或未知扩展可能收集简历、Cookie 或账号信息。
- 根因：浏览器扩展拥有页面读取权限，外部服务的隐私边界不可默认信任。
- 方案：默认不调用外部 API；设置、岗位摘要和队列只保存在本地；后续接入 AI 必须显式授权并说明发送字段。
- 性能变化：离线评分延迟低且稳定，但个性化文案能力有限。
- 临时方案：使用本地模板变量生成招呼语，不上传完整简历。

### scenario_id: PLATFORM_ADAPTER_REGISTRY

- 问题：多个招聘网站的岗位卡片结构不同，直接在一个内容脚本里堆选择器会互相污染。
- 根因：平台差异和通用业务规则没有隔离，改一个站点容易影响其他站点。
- 方案：将每个平台拆成 `src/content/adapters/` 下的独立文件，由注册入口按域名选择 `cardSelectors` 和字段选择器；通用层继续只处理评分和队列。
- 性能变化：每个页面只遍历当前平台的选择器，避免无关站点查询。
- 验证：Manifest 已覆盖 11 个目标域名，构建测试校验所有 host permission；真实 DOM 仍需逐站人工验收。

### scenario_id: APPLICATION_FORM_VARIANCE

- 问题：网申表单字段、步骤和自定义控件差异大，单一通用脚本容易误填。
- 根因：表单字段没有统一公开协议，附件、开放问答和验证码还涉及高风险外部操作。
- 方案：作为候选模块采用 DOM 识别优先、站点适配器补充、多模态可选兜底，并展示识别置信度。
- 性能变化：常规字段保持本地即时识别；只有低置信度字段才考虑额外分析。
- 临时方案：本轮不开发网申模块，当前版本只提供岗位准备和招呼语复制。

### scenario_id: LOCAL_DEMO_HOST

- 问题：直接打开 `file://` 演示页时，Chrome 内容脚本不会按真实平台适配器运行。
- 根因：扩展匹配规则默认只覆盖招聘网站 HTTPS 域名，且文件页没有平台 hostname。
- 方案：增加受限的 localhost 演示适配器和 `python -m http.server` 启动方式；不增加任何真实平台权限。
- 性能变化：只对本地演示页面增加一次精确 class 查询。
- 验证：构建测试校验 localhost match；Playwright 加载 `dist` 后访问 `http://localhost:8087/boss-mock.html`，页面出现本地演示浮层和 2 个匹配岗位；真实平台权限不受影响。

### scenario_id: BATCH_QUEUE_ONLY

- 问题：逐个点击岗位卡片加入准备队列仍然影响海投效率。
- 根因：候选岗位筛选结果已经在页面内，但缺少一次性写入本地队列的入口。
- 方案：增加“加入全部匹配”按钮，逐条调用本地队列消息；该流程不打开详情、不点击沟通、不发送消息。
- 性能变化：批量操作只传输已解析的岗位对象，避免重新扫描 DOM；队列仍受 30 条上限保护。
- 验证：静态测试检查批量入口存在；真实平台需由用户在列表页人工验收。

### scenario_id: LAZY_LOAD_PRELOAD

- 问题：招聘网站使用懒加载时，当前 DOM 只包含首屏岗位，批量筛选范围不足。
- 根因：列表新增依赖用户滚动，扩展没有提供可控的加载入口。
- 方案：增加用户主动触发的渐进滚动预加载，最多 40 轮；连续 3 轮卡片数量不增长即停止，随后仍由现有 MutationObserver 负责扫描。
- 性能变化：只在用户点击按钮后运行，单轮等待 450ms，避免持续后台滚动。
- 验证：类型检查、构建和静态测试通过；真实平台需观察页面懒加载是否正常。

### scenario_id: DETAIL_APPLICATION_STATUS

- 问题：岗位详情页可能是聊天岗位，也可能是网申或未知入口；静默加入队列会让用户误以为都能沟通。
- 根因：列表页无法可靠知道详情页最终动作，平台按钮文案和结构也会变化。
- 方案：详情适配器读取沟通按钮文案，展示“可沟通/可能网申/需人工确认”；加入队列失败时将错误显示在按钮上。
- 性能变化：只在详情页打开浮层时读取一次按钮文本。
- 验证：类型检查、构建和契约测试通过；真实页面需人工确认状态文案。

### scenario_id: MANUAL_COMPLETION_TRACKING

- 问题：用户打开岗位并在平台手动完成投递后，扩展没有本地完成状态。
- 根因：队列只有待处理状态，缺少“已打开”和“已处理”的人工确认入口。
- 方案：打开岗位链接时记录 `opened`；用户完成平台操作后在弹窗点击“标记已处理”，记录 `done`，不触发任何平台提交。
- 性能变化：只更新本地 `chrome.storage.local` 队列，不增加页面请求。
- 验证：类型检查、构建和静态测试通过。

### scenario_id: MULTI_IDENTITY_MATCH

- 问题：Boss 列表和详情响应可能使用不同的岗位标识字段，单一 ID 会造成错配或重复记录。
- 根因：同一岗位响应可能同时包含 `encryptJobId`、`securityId`、`lid`，不同页面返回字段不完全一致。
- 方案：岗位对象保存全部可用身份键，合并时优先做集合交集匹配，再使用岗位名+公司+薪资签名兜底。
- 性能变化：每次匹配只比较有限的字符串集合，不增加网络请求。
- 验证：`pnpm test:api` 覆盖多身份键提取、交集匹配和合并结果。

### scenario_id: DOM_CARD_FALLBACK

- 问题：岗位卡片字段可能因页面版本、字体加密或 class 变化而缺失，固定选择器会直接丢弃岗位。
- 根因：解析逻辑和平台选择器耦合，未读取岗位链接身份键，也没有岗位名清洗和文本兜底。
- 方案：新增 `dom-parser.ts`，集中处理 class 片段兜底、薪资剥离、岗位详情链接 ID、data 属性 ID 和岗位文本摘要；平台文件只提供差异选择器。
- 性能变化：每张卡片增加有限的属性和链接遍历，避免重复网络请求。
- 验证：本地演示浏览器验证通过，接口/适配器契约测试通过；真实平台仍需登录态验收。

### scenario_id: EMPTY_DETAIL_LINK_FALLBACK

- 问题：没有岗位链接的本地/部分平台卡片会让扫描在首轮直接中断。
- 根因：`new URL("", currentPage)` 是合法 URL，空字符串被错误判定为可用链接，随后读取了空节点的 `href`。
- 方案：先判断原始链接非空，再执行协议校验；空链接统一回退到当前页面 URL。
- 性能变化：增加一次空字符串判断，无额外 DOM 查询。
- 验证：localhost 浏览器回归复现并修复，`pnpm test` 通过。

### scenario_id: LOCAL_QUEUE_EXPORT

- 问题：候选岗位只保存在浏览器本地，难以离线复盘和整理。
- 根因：首版只实现队列读写，没有导出边界清晰的结构化记录。
- 方案：弹窗生成 UTF-8 CSV，只导出岗位公开字段、匹配分、状态和岗位链接；使用 Blob 下载，不访问外部接口。
- 性能变化：导出成本与队列条数线性相关，默认上限 30 条，浏览器端即时完成。
- 验证：类型检查和构建测试通过；导出动作仅发生在用户点击“导出 CSV”后。

### scenario_id: BOSS_API_DOM_MERGE

- 问题：Boss 岗位卡片字段不完整，薪资可能是字体加密，单靠 DOM 会导致评分和记录缺少 JD 信息。
- 根因：列表页是 SPA，岗位详情通过异步接口加载；卡片顺序会因懒加载和刷新变化，不能依赖索引硬匹配。
- 方案：在页面主世界只读观察 Boss 岗位 GET 响应；`boss-api.ts` 提取公开字段，优先用岗位 ID，再用岗位名+公司签名与 DOM 卡片合并。桥接不修改请求、不发起新请求。
- 性能变化：只对匹配岗位接口 clone 一次响应并递归遍历有限深度，列表扫描仍由当前平台适配器控制。
- 验证：本地构建、类型检查和 localhost 浏览器验收通过；真实 Boss 接口字段需要用户登录后验收。

### scenario_id: BOSS_BRIDGE_HANDSHAKE

- 问题：页面主世界桥接在 `document-start` 执行，内容脚本在 `document-idle` 执行，首批接口响应可能早于监听器到达。
- 根因：`window.postMessage` 没有历史消息队列，单向广播会丢失早期事件。
- 方案：内容脚本发送一次 `READY` 握手；桥接在握手前只缓存最近 20 条岗位 GET 响应，握手后按顺序释放。
- 性能变化：只增加有限内存队列，超过 20 条丢弃最早事件，避免页面初始响应异常占用内存。
- 验证：类型检查和构建测试通过；真实 Boss 首屏响应需登录态验收。

### scenario_id: REFERENCE_SELECTOR_PORT

- 问题：通用选择器无法证明能够识别真实招聘网站页面。
- 根因：平台 DOM 选择器不是稳定公开 API，仓库之间也可能因页面版本存在差异。
- 方案：把 `get_jobs-main` 中已经使用过的 Boss、智联、前程无忧和猎聘选择器加入对应适配器，同时保留通用兜底；不复制其投递点击逻辑。
- 性能变化：当前平台只增加少量候选选择器，仍由单次适配器扫描执行。
- 验证：代码构建和本地演示通过；真实站点需登录后逐站确认字段和列表加载行为。

### scenario_id: PLATFORM_HEALTH_STATUS

- 问题：真实平台验收时，无法快速区分“没有匹配岗位”和“扩展没有识别到岗位卡片”。
- 根因：页面浮层只显示匹配数，没有暴露平台名、卡片总数和最近扫描时间。
- 方案：内容脚本响应 `GET_CONTENT_STATUS`，弹窗展示平台、已识别岗位数和匹配数；未加载内容脚本时明确提示。
- 性能变化：仅在打开弹窗时读取一次状态，不增加页面轮询。
- 验证：类型检查、构建和静态测试通过；真实平台需人工确认各站点卡片数。

### scenario_id: API_ADAPTER_CONTRACT

- 问题：只靠构建通过无法证明接口字段提取、岗位去重和平台域名路由正确。
- 根因：这些逻辑跨越共享模型、Boss 解析器和 11 个适配器，容易出现字段改名或域名子域误路由。
- 方案：增加无网络契约测试，固定最小 Boss JSON 响应，验证 ID 去重、字段提取、DOM/API 合并和全部平台 hostname 路由。
- 性能变化：测试只处理内存 fixture，不影响扩展运行时性能。
- 验证：`pnpm test:api` 和 `pnpm test` 通过；真实页面字段仍需用户登录态验收。

### scenario_id: PAGE_BRIDGE_ORIGIN_CHECK

- 问题：同页脚本可以调用 `window.postMessage`，若只检查自定义 source 字段，可能伪造岗位事件。
- 根因：页面消息总线本身不提供业务身份认证，扩展必须先校验事件来源。
- 方案：内容脚本同时校验 `event.source === window` 和 `event.origin === location.origin`，并继续只提取公开岗位字段。
- 性能变化：每条消息增加一次字符串比较，成本可忽略。
- 验证：类型检查、构建和静态测试通过。
